# Patching — updating SABIHA ERP without a full reinstall

This explains how future updates work: small "patch" files you apply
in place, instead of deleting everything and reinstalling from scratch.

## The short version

1. I (Claude) give you a small zip file, e.g. `patch-3.1.0.zip`.
2. You drop it into this `toybox-server` folder.
3. You double-click `apply-patch.bat` (or run `./apply-patch.sh` on
   Mac/Linux), type the filename when asked, and press Enter.
4. It backs up your current files, applies the patch, and reinstalls
   dependencies only if something new is needed. Your data is never
   touched.
5. Restart with `start.bat` and check the version number in the
   sidebar to confirm the update landed.

## Why this works safely

Everything in this app falls into one of two groups:

**Group A — App code (safe to overwrite, this is what patches contain):**
`server.js`, `auth.js`, `db.js`, everything in `routes/`, everything in
`public/` (`index.html`, `app.js`, `style.css`, `assets/`), and
occasionally `package.json` if a new feature needs a new dependency.

**Group B — Your data (a patch must NEVER touch these):**
`data/` (your live database), `backups/` (your saved backups), `.env`
(your unique login secret, generated once on first run). `node_modules/`
also isn't part of a patch — it's regenerated by `npm install` when
needed, not shipped as files.

Because a patch only ever contains Group A files, applying one is safe by
construction — there's nothing in a patch that *could* overwrite your
data even by accident, as long as patches are built the way described
below.

## How database changes are handled (no manual SQL, ever)

If a future update needs a new column or table (say, adding a "Barcode"
field to Products), it's added in `db.js` using a pattern already built
into this app — an `ensureColumn(table, column, definition)` call. When
the patched `db.js` runs against your *existing* database file, it checks
whether each column already exists and adds it if not, using `ALTER
TABLE`. Nothing is dropped, nothing is recreated, none of your existing
rows are touched. This happens automatically the moment you restart the
app after a patch — you don't do anything extra for it.

For the rare case where existing *data* itself needs transforming (not
just the schema — e.g. renaming a status value everywhere it appears), a
patch can optionally include a one-time `migrate.js` script. If a patch
comes with one, its README will say so explicitly and `apply-patch.bat`
will mention it; otherwise there's nothing to run.

## How a patch is created (for reference — I do this on my end)

When you ask for changes in a future conversation, here's what happens
behind the scenes to produce `patch-X.Y.Z.zip`:

1. I compare the new versions of files against what you currently have
   installed, and identify exactly which files changed or were added.
2. I zip up *only* those files, preserving their folder path (e.g.
   `public/app.js`, `routes/transactions.js`) so extracting the zip into
   your `toybox-server` folder overwrites exactly the right files in
   place.
3. `data/`, `backups/`, `.env`, `node_modules/`, and `dist/` are never
   included.
4. `package.json`'s `"version"` field is bumped (e.g. `3.0.0` →
   `3.1.0`), and — only if a new dependency was actually added —
   `package.json` itself is included in the patch so `npm install`
   picks it up. Most patches won't need this; `npm install` after a
   patch is nearly instant when nothing new was added, since npm just
   confirms everything already matches.
5. I'll also give you a short changelog listing what changed.

If you ever want to apply a patch that didn't come from me (say, a file
someone else sent you), the same rule applies: it should only contain
files from Group A above, with the same folder structure as this
project, zipped from the `toybox-server` folder level (so the zip's
top-level entries are `public/`, `routes/`, `server.js`, etc. — not a
wrapping folder).

## Rolling back a patch

Every time you run `apply-patch.bat`, it saves a full copy of your
previous app files (not your data — that's never at risk) into
`patches\backup-<timestamp>\` before making any changes. If a patch
ever causes a problem:

1. Close the app if it's running.
2. Copy the files from the relevant `patches\backup-<timestamp>\`
   folder back into `toybox-server`, overwriting the patched files.
3. Run `npm install` again in case the patch had changed dependencies.
4. Restart with `start.bat`.

Your data in `data\erp.sqlite` is completely unaffected by any of this,
since patches and rollbacks never touch it.

## If you're running the standalone .exe (Option 2)

If you built `SABIHA-ERP.exe` via `build-exe.bat`, a patch to the source
code doesn't update that `.exe` automatically — the `.exe` is a frozen
snapshot from when you built it. After applying a patch to the source
folder, run `build-exe.bat` again to produce a new `.exe` with the
update included. Your data in `dist\data` is untouched either way, since
it lives outside the `.exe` file itself.
